# kahyad/internal/policy — W3-02 wire schema

`POST /policy/check` `{tool_name, tool_input, scope?, task_id, trace_id, preflight?}` → `{decision: "allow"|"needs_approval"|"deny", reason?, rule, pending_approval_id?, token?}`. `class` is never client-supplied — resolved from the loaded `policy.yaml`. `token` appears only on `allow` for a non-R (side-effectful) class; `pending_approval_id` only on `needs_approval`. `preflight: true` (B-1, `CheckInput.Preflight` — the worker's `can_use_tool`) decides and ledgers (`preflight:true`) but mints nothing: no pending row, no token, no undo window, no grant redemption.

**Approval loop (B-1, `approval_loop.go`).** `Engine.Approve` persists a single-use grant (`approval_tokens.grant_kind='approval'`, `pending_approval_id` = the answered row) bound to that row's exact task_id/tool/scope/approved_bytes_hash. The next binding `Engine.Check` for the same task and bytes — the parked tool call's own re-check (kahyad/internal/server `checkWithApprovalWait`, `CheckInput.NoMintPending`: never a second pending row), or the model's identical retry within the 10-minute token TTL — **redeems** it (`redeemApprovedGrant`: burned with the single-use UPDATE, ledgered `approval_grant_redeemed`, before the W3 branch so a written local W3 approval executes exactly once) and answers `allow` with a fresh `grant_kind='exchanged'` token for the unchanged `ConsumeToken`. Other bytes, another task, an expired (`approval_grant_expired`) or halt-revoked grant never redeem. `pending_approvals.decision` records `approved|denied|invalidated`; `SetApprovalDecidedHook` fires after Approve (grant minted), Deny and each halt invalidation; `PendingApprovalDecision` reports `approved` only once the grant row exists. `BootstrapLevels` seeds config `autonomy_bootstrap_levels` rows only where none exist (`autonomy_bootstrapped` / `autonomy_bootstrap_rejected`).

`pending_approval_id` (post-security-review amendment) is a server-issued, single-use, DB-tracked reference: `Engine.Check` inserts a `pending_approvals` row (32 random bytes hex id, bound to the RESOLVED tool/class/scope/task_id/trace_id/approved_bytes_hash, 10-minute TTL) and returns its id — it is opaque and carries no caller-decodable meaning. `Engine.Approve`/`Deny` look the row up by id and atomically single-use-consume it (`consumed_at IS NULL`); a forged, expired, or already-consumed id is rejected outright, before any token is minted or any bookkeeping runs. W3-06 additionally persists the row's exact `tool_input` bytes (not just their hash) so `kahya approvals`/`kahya approve <id>` can render the real byte-exact WYSIWYE diff — see `Engine.ListPendingApprovals`/`GetPendingApprovalDetail`, both read-only (never consume).

`POST /policy/consume-token` `{token, tool, class, scope, task_id, trace_id, tool_input}` → `{ok, error?}`. Side-effectful tools MUST call this, with the EXACT bytes they are about to execute, immediately before executing. Single-use; any failure demotes the token's REAL bound `(tool,class,scope)` — persisted on `approval_tokens` at mint time and recovered by `token_hash` — never the `tool`/`class`/`scope` this request body happens to claim, and ledgers `token_verify_failed`. A hash matching no token row at all demotes nothing (there is no real triple to punish) but still ledgers. W3-06: the hash compared is `approvedBytesHash`, which routes `tool_input` through `kahyad/internal/canon.CanonicalizeBytes` (NFC-normalize, strip bidi/zero-width/other-Cf control code points — confusables are flagged, never rewritten) before hashing — an NFD-vs-NFC difference in the same path collapses to an identical hash, while a genuine byte mutation (a trailing space, a homoglyph swap) still changes it. `mintToken`'s own token-hash (the lookup key derived from the random token bytes themselves) is a separate, plain `rawBytesHash` — never canonicalized, since a random credential carries no WYSIWYE meaning.

`POST /policy/feedback` `{kind: "approve"|"deny"|"undo", pending_approval_id?, surface?, trace_id?}` → `{ok, error?}` (since B-1 no raw token on the wire — `FeedbackResult.Token` stays an in-process value only). `approve` persists a single-use grant the parked tool call redeems (W3 requires `surface:"local"`, checked against the pending_approvals row's real class — a rejected non-local W3 approval attempt does NOT consume the id, so it stays usable for a later local approval, and ledgers `w3_nonlocal_approval_rejected`, Go-side, so Telegram/W3-07 can never be wired to approve a W3 action); any non-local surface (anything but the literal `"local"`) additionally requires the tool's `policy.yaml` rule to be `reversible: true` — otherwise `ErrNonLocalRequiresReversible`, ledgered `nonlocal_irreversible_approval_rejected`, id not consumed (B-11, HANDOFF §4 "uzaktan onay, yalnız geri-alınabilir eylemler"); `deny`/`undo` demote.

`GET /policy/approvals` → `{approvals: [{id, tool, class, scope, summary, minted_at}]}` (W3-06, `kahya approvals`) — every not-yet-consumed, not-yet-expired pending approval, oldest first. `GET /policy/approvals?id=<id>` → the single row's full rendered WYSIWYE diff (`kahya approve <id>`'s own lookup — read-only, does not consume).

`GET /policy/state` → `{states: [{tool, class, scope, level, consecutive_approvals, updated_at}]}`.

`POST /policy/promote` `{tool, class, scope}` → `{level}` — the only path that ever raises a level (`kahya autonomy promote`). Control route: requires `X-Kahya-Control-Secret` (kahyad/internal/server/controlauth.go), unreachable from a worker.

`POST /policy/undo` `{trace_id}` → `{ok, tool, task_id}` — triggers an open undo window; recipe execution is the owning tool's job (W3-03).
